# 2026-10-06 처리 구조 비교: 예비 측정

## 조건과 측정 범위

- 보드: Raspberry Pi 4, aarch64. 커널 `6.1.21-v8+`.
- GStreamer 1.18.4, OpenCV 4.5.1, C++17.
- 소스 기준: `9e9d7d7454be1dbce5f3141616938f693613a360` 이후 로컬 수정 상태.
  이번 계측 코드·시험 도구는 미커밋 상태이며 기존 운영 서비스와 별도 실행했다.
- 실행: `./tools/performance/run_suite.sh 20 1 5`.
- 조건별 20초, 반복 1회, 처음 5초 제외. 분석 구간은 종료 처리에 따라 약 15.0~15.3초.
- 입력·인코더·버퍼 정책은 [시험 조건](README.md#공통-조건)에 정의한 합성 영상 조건이다.
- 모델: 설치된 Caffe MobileNet-SSD, 기존 person 필터·NMS 설정 사용.
- 순서: off → async1 → async2 → async3 → sync2 → fifo2.
- 다른 서비스: `ptz-camera.service`, `ptz-servo.service` 활성 상태. 두 서비스를 재시작하지 않았다.
- CPU는 100%가 코어 하나다. 아래 값은 benchmark 프로세스만의 사용량이다.
- 온도: 조건별 최대 약 60.9~75.5°C로 올라갔다. 전·후 `get_throttled`는 전 조건 `0x0`.
- 주변 온도/냉각 구성은 별도 측정하지 않았다. 순차 실행의 온도 편향을 배제하지 못한다.
- 원본 위치: `tools/performance/results/20261006-155249-175252/`.
  조건 파일, 이벤트/자원 CSV, 스로틀링 값, 실행 결과, 시험 실행 파일 SHA-256을 보관했다.
- 마지막 요약 단계의 셸 오류는 원본 CSV로 복구했다. 원인과 재검증은
  [트러블슈팅](../../troubleshotting.md)에 기록했다.

## 설계 판단

### 송출과 추론을 분리한 이유

최신 프레임을 쓰는 비동기 조건은 약 30개의 인코딩 출력 버퍼/s를 유지했다.
공유 경로에서 추론 완료를 기다린 조건은 약 11개/s였다. 이 조건에서는 느린 연산이
공유 경로를 막는 영향을 관측했다. 운영 구조는 별도 queue와 탐지 스레드를 사용해
이 대기가 송출 경로에 직접 전파되지 않게 한다. CPU를 공유하므로 자원 경쟁은 남는다.

### 최신 프레임을 우선한 이유

FIFO 조건은 추론 함수 자체가 더 빨랐지만 결과가 나온 시점의 프레임은 훨씬 오래됐다.
최신·2스레드 조건의 평균 결과 나이는 약 336ms였다. 실시간 추적에서는 모델 실행
시간만 보지 않고 결과의 신선도와 송출 유지 여부를 함께 봐야 한다.
실제 운영 코드는 600ms를 넘은 결과로 서보를 이동시키지 않는다.

### 추론 스레드를 2개로 둔 이유

1스레드는 CPU 사용이 적었지만 추론이 느렸다. 이번 짧은 시험에서는 2스레드가
3스레드보다 추론 평균·p95와 결과 나이가 낮았다. 3스레드가 항상 나쁘다는 결론은
내리지 않는다. 장시간 반복과 조건 순서 교대로 온도 영향을 확인해야 한다.

### 순차 추론과 단일 제어 이벤트 루프를 유지한 이유

한 탐지 스레드는 프레임 하나의 추론을 완료한 다음 해당 결과에서 이동량을 계산한다.
서보 서비스는 짧은 TCP/키보드 명령을 한 이벤트 루프에서 처리하고 버튼은 pigpio
콜백으로 받는다. 각도/GPIO 공유 상태는 mutex로 보호한다.
이번 합성 시험은 이 제어 구조의 실물 응답 시간을 입증하지 않는다. 가짜 pigpio 회귀
시험으로 기존 제어 동작과 `command/button → gpio_write` 로그 연결을 확인했다.
실제 서비스의 계측 로그로 명령 처리 지연을 별도 수집해야 한다.
