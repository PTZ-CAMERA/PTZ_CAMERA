## 카메라 송출을 C++로 전환

- `pi/camera_stream/src/main.cpp`에 C++17/GStreamer 송출기를 작성했다. IMX219 영상을 1280×720, 30fps로 캡처해 H.264로 인코딩하고 MediaMTX의 `rtsp://127.0.0.1:8554/cam`에 발행한다. 기존 `libcamera-vid | ffmpeg` 셸 송출 스크립트는 제거했다.
- `libcamerasrc → videoconvert → x264enc → h264parse → rtspclientsink` 경로를 사용한다. GStreamer의 `v4l2h264enc`는 이 Pi에서 프레임 처리 오류가 나서 소프트웨어 인코더로 대체했다. 송출 중 C++ 프로세스 CPU 사용량은 약 1코어 이상이었다.
- CMake와 설치 스크립트, 서비스 설정을 갱신했다. RTSP에서 H.264 Constrained Baseline 1280×720/30fps 프레임을 디코딩했고 WebRTC 페이지의 HTTP 응답도 확인했다. PC Qt 화면에서의 영상 품질은 별도 확인이 필요하다.
- MediaMTX는 C++ 송출기의 영상을 받아 RTSP·WebRTC·HLS 시청자에게 전달하는 서버다. `runOnDemand`로 첫 시청자가 접속할 때만 송출기를 시작하고 마지막 시청자가 떠난 뒤 5초에 종료하도록 했다. 감시 타이머는 시청자가 없으면 카메라를 깨우지 않도록 로컬 메트릭을 확인한다.

## Qt PTZ 제어 연결

- Qt `NetworkClient`가 `192.168.0.92:5000`에 `PTZ:LEFT/RIGHT/UP/DOWN/CENTER`를 개행으로 보낸다는 코드를 확인했다. Pi의 `servo_test`에 TCP 5000 서버를 추가해 PAN/TILT 5° 이동과 중앙 복귀에 매핑했다. GPIO17 버튼과 기존 터미널 키 제어는 유지했다.
- `ptz-servo.service`와 설치 스크립트를 추가하고 실제 Pi에서 서비스를 실행했다. 로컬 TCP 테스트로 LEFT/RIGHT/UP/DOWN/CENTER 수신과 각도 로그를 확인했다. `TRACK:ON/OFF`는 추적 기능이 없어 오류로 처리한다.
- 서비스가 pigpio 잠금을 소유한 상태에서 두 번째 `servo_test`를 직접 실행하면 `/var/run/pigpio.pid` 잠금 오류가 났다. 기본 터미널 실행은 현재 로컬 TCP 서비스에 접속해 키를 전달하도록 고쳤고, `--direct`는 서비스 중지 후 GPIO 직접 테스트용으로 분리했다. 시스템 서비스 종료 시 pigpio의 SIGCONT 오류도 수정했다.
- Pi 서비스 로그에 TCP 연결·해제, 수신 명령, 각도 변경이 표시되도록 했다. `journalctl -u ptz-servo.service -f`로 확인한다. 로컬 터미널 명령은 도달했으나 PC Qt에서 들어온 TCP 연결은 조사 시점에 관찰되지 않았다. Qt `sendLine()`은 연결되지 않으면 명령을 보내지 않으므로 Qt의 `connected`/`connectionError` 상태와 재연결을 확인해야 한다.

## RTSP 전송 방식과 지연

- RTSP/TCP와 RTSP/UDP의 패킷 손실·지연 차이를 `docs/rtsp_tcp_udp.md`에 정리했다. Pi MediaMTX는 현재 `[udp, tcp]`를 허용하고 TCP 8554와 UDP 8000(RTP)·8001(RTCP)을 연다. Pi의 C++ 송출기에서 MediaMTX로 들어가는 연결은 TCP를 유지한다.
- Pi에서 FFmpeg로 RTSP/UDP와 RTSP/TCP 각각 한 프레임을 디코딩했다. Qt에서 UDP를 쓰려면 같은 RTSP URL을 유지하면서 **Qt 재생기에서 UDP 전송을 선택**해야 한다. Qt UI에는 아직 UDP 선택 항목이 구현되지 않았다.
- UDP 설정을 적용하는 과정에서 MediaMTX가 RTSP 수신부를 다시 열어 기존 PC RTSP 연결을 끊었다. Qt에서 재연결이 필요하다.
- 지연의 원인은 아직 측정되지 않았다. Pi 송출 코드에는 재생/지터 버퍼를 임의로 설정하지 않았다. MediaMTX의 송신 대기열은 기본 512패킷이고 UDP 소켓 수신 버퍼는 OS 기본값을 사용한다. **Qt 영상 재생기의 버퍼 값은 Qt 영상 코드가 Pi 저장소에 없어 미확인**이다. 앞서 언급한 150~250ms는 적용값이 아니라 시험 제안이다.

- RTSP 지연을 줄이려면 먼저 Qt 영상 재생 백엔드와 수신/지터 버퍼 설정을 확인하고, 첫 화면 지연과 재생 중 지연을 따로 측정한다.

- 원격 `main`에는 `9e9d7d7`까지 푸시됐다. 그 이후의 터미널 클라이언트·추가 로그·RTSP/UDP·문서 변경은 **로컬에만 있다**. 사용자가 요청한 규칙에 따라 앞으로 푸시 전에 반드시 허락을 받는다.

  수동 PTZ 명령이나 GPIO17 버튼은 자동 추적을 해제한다. Qt가 이해하는
  `CAMERA:CONNECTED/DISCONNECTED`, `DETECT`, `NO_DETECTION` 메시지를 전달한다.
- 두 C++ 프로그램을 빌드했고 모델 로딩·추론이 성공했다. 모델 원본의 예제 사진
  7장에서 사람 탐지 결과가 나온 사진은 3장이었다. 이 숫자는 탐지 정확도 평가가
  아니다.
- 현재 설치된 systemd 서비스에서 RTSP 영상 디코딩이 성공했다. 시험 클라이언트는
  `CAMERA:CONNECTED`와 `NO_DETECTION`을 받았다. 시험 장면에는 확인 가능한
  사람이 없어서 실제 사람을 따라 움직이는 서보 동작은 **검증하지 못했다**.
- 실시간 송출과 탐지를 동시에 실행한 짧은 시험에서 OpenCV 추론은 약
  300~320ms/프레임, 프레임 나이는 약 600~700ms였다. 현재 코드는 600ms보다
  오래된 탐지 결과를 서보 제어에서 제외하므로, 이 상태에서는 자동 제어 반응이
  부족할 수 있다. 해당 성능 문제는 `troubleshotting.md`에도 기록했다.
- 송출 없이 실행한 모델 벤치마크에서는 스레드 1개 약 412ms, 2개 약 229ms,
  3개 약 192ms/프레임이었다. 3개 스레드가 송출과 함께 실행할 때도 유리한지는
  아직 확인하지 않았다.
- **중단 시 운영 상태:** `ptz-servo.service`, `ptz-camera.service`는 active이고
  `TRACK:STATUS` 응답은 `TRACK:OFF`다. 카메라 송출기는 시청자가 있을 때만
  시작한다. 마지막 코드 변경(추론 벤치마크 명령과 입력 프레임 나이 로그)은
  빌드됐지만 시스템 설치본에는 다시 반영하지 않았다. 설치된 서비스는 그 직전
  빌드로 실행된다. 기존 핑크색 프레임 원인은 여전히 미확정이다.
