# 2026-10-01 PTZ 프로젝트 작업 기록

## 오늘 결정한 구성

- PTZ는 Raspberry Pi 4만 사용한다. ESP32-C6/UART 방식은 현재 프로젝트에서 제외했다. 이전 자료는 `/root/ptz_project_legacy_20261001/`로 옮겨 두었다.
- Qt 화면은 사용자의 PC에서 개발한다. Pi는 서보 제어와 카메라 영상 송출을 담당한다. PC의 Qt 프로젝트는 이 작업 공간에 없어 Qt 코드 자체는 아직 수정하지 않았다.

## 서보 제어

- `pi/servo_test/src/main.cpp`: C++17과 pigpio C API로 MG90S 두 개를 제어한다. PAN 신호는 BCM GPIO18, TILT 신호는 BCM GPIO19, 중앙 복귀 버튼은 BCM GPIO17(내부 pull-up, active-low)이다.
- 시작 시 두 축을 90도로 이동한다. 터미널 `a`/`d`는 PAN, `w`/`s`는 TILT, `c`는 중앙 복귀, `q`는 종료다. 버튼에는 debounce를 적용했다.
- 현재 소프트웨어 제한은 PAN **25~155도**, TILT **40~140도**다. PAN은 처음의 30~150도에서 양쪽 5도씩 넓혔다. 물리적 끝점과 간섭 여부는 아직 검증하지 않았다.
- `pi/servo_test/CMakeLists.txt`로 빌드했으며 C++17, `pigpio`, `pthread`, `rt`를 연결한다. 컴파일은 통과했다. 사용자 하드웨어 테스트에서 PAN/TILT 동작에 대한 언급이 있었으나 최종 기구 상태는 확정하지 않았다.
- 배선: MG90S 두 개의 전원은 외부 4.8~6V, Pi GND와 외부 전원 GND 공통, Pi GPIO에는 서보 신호만 연결한다.

## 카메라와 영상 송출

- Pi의 IMX219 CSI 카메라를 `libcamera-vid --list-cameras`로 인식했다. 케이블 변경 중 한때 인식되지 않았고, 다시 연결한 뒤 정상 인식 및 영상 수신을 확인했다.
- Raspberry Pi OS Bullseye에서는 `libcamera-vid`가 H.264를 만들고 FFmpeg가 재인코딩 없이 MediaMTX로 RTSP 발행한다. 구성 파일은 `pi/camera_stream/mediamtx.yml`, 실행 파이프라인은 `pi/camera_stream/publish.sh`다.
- MediaMTX v1.21.1 ARM64를 `/usr/local/bin/mediamtx`에 설치하고 `ptz-camera.service`를 등록했다. 서비스는 부팅 시 자동 실행되도록 **enabled** 상태다.
- 확인된 스트림은 H.264 **1280×720, 30 fps**다. Pi LAN 주소는 기록 시점에 `192.168.0.92`였다. 주소는 바뀔 수 있으므로 다음에 `hostname -I`로 확인한다.
- PC 접속 주소: WebRTC/Qt WebEngine `http://192.168.0.92:8889/cam/`, RTSP/VLC `rtsp://192.168.0.92:8554/cam`, HLS 대체 주소 `http://192.168.0.92:8891/cam/`. WebRTC 영상 전송에는 UDP 8189도 사용한다.
- Qt Widgets에서는 `QWebEngineView::load(QUrl("http://192.168.0.92:8889/cam/"))`를 사용한다. PC 쪽 Qt 프로젝트와 실제 재생 화면의 최종 통합은 아직 하지 않았다.

## 오늘 해결하거나 조사한 문제

- **pigpio 실행 실패:** MediaMTX HLS와 pigpio가 모두 TCP 8888을 사용했다. HLS를 8891로 옮긴 뒤 `gpioInitialise()` 성공을 확인했다.
- **스트림 중단:** 카메라는 인식되지만 Pi에서 MediaMTX로 발행하는 영상이 멈춰 RTSP가 404가 된 적이 있다. 서비스를 재시작해 복구했다. `ptz-camera-watchdog.timer`를 추가해 30초마다 실제 프레임을 검사하고, 연속 실패 시 서비스를 재시작하도록 했다. 근본 원인은 아직 확정하지 않았다.
- **간헐적 핑크 화면:** 네트워크로 보내기 전 Pi에 직접 녹화한 20초 H.264 파일의 593프레임 중 2프레임(9.84초, 17.67초)에서 같은 핑크색 손상을 확인했다. 따라서 PC/Qt 재생만의 문제는 아니다. 별도의 12초 MJPEG 녹화에서는 재현되지 않았다. CSI 케이블·커넥터, 카메라, Pi 영상 처리, H.264 인코딩 중 어느 지점인지는 아직 구분되지 않았다. 당시 `vcgencmd get_throttled`는 `0x0`이었다.
- 각 사건의 상세 증거와 조치는 `troubleshotting.md`에 기록했다. 앞으로도 트러블슈팅할 때마다 그 파일에 새 항목을 추가한다.

## 세션 종료 시 상태와 재개 명령

- 사용자 요청에 따라 카메라 스트림은 현재 **inactive(중지)** 상태다. 자동 시작 설정은 **enabled** 상태이므로 Pi가 재부팅되면 다시 켜진다. 감시 타이머는 active지만, 사용자가 의도적으로 스트림을 중지한 동안에는 재시작하지 않는다.
- 서보 테스트 프로그램도 현재 실행 중이지 않다.

```sh
# 카메라 시작 / 중지 / 상태 확인
sudo systemctl start ptz-camera.service
sudo systemctl stop ptz-camera.service
systemctl status ptz-camera.service

# 서보 프로그램 빌드 / 실행
cd /root/ptz_project/pi/servo_test
cmake -S . -B build
cmake --build build -j4
sudo ./build/servo_test
```

다음 작업은 핑크색 프레임의 원인 분리(전원을 끈 상태에서 CSI 연결 확인 후 H.264/MJPEG 장시간 비교), 스트림 장시간 안정성 확인, PC의 Qt 화면 연결이다.
