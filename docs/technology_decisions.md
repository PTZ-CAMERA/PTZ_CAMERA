# PTZ 카메라 기술 선택과 판단 근거

이 문서는 Raspberry Pi 4 기반 PTZ 카메라의 기술 선택 이유를 기록한다. **사용 중**인
구성과 **검토 중**인 설계를 구분한다. 속도나 안정성이 실측되지 않은 후보를 확정된
성능으로 기록하지 않는다. 기술을 추가하거나 교체할 때 이 문서에 선택 이유, 대안,
검증 결과를 이어서 남긴다. 실행 중 발생한 문제의 조사·조치는
[트러블슈팅 기록](../troubleshotting.md)에 남긴다.

## 판단 기준

사람을 화면 중앙에 유지하는 기능에는 모델의 단독 FPS보다 다음 항목이 중요하다.

1. 촬영 시각부터 Qt 화면 표시까지의 영상 지연
2. 촬영 시각부터 서보 명령까지의 추적 지연과 오래된 프레임의 비율
3. 거리·조명·가림 변화에서 사람을 놓치는 빈도와 탐지 위치의 흔들림
4. 영상 송출과 탐지를 동시에 실행할 때의 CPU 사용량·온도·프레임 누락
5. 기존 C++ 프로젝트와 Qt 제어 프로토콜의 통합 비용

평균뿐 아니라 지연이 큰 구간도 측정한다. 비교 대상에는 동일한 카메라 장면과 송출
설정을 사용한다.

## 사용 중인 기술

| 영역 | 선택 | 이유와 현재 상태 |
| --- | --- | --- |
| 실행 환경 | Raspberry Pi 4, C++17, CMake | 카메라·서보를 Pi에서 실행하며, 프로젝트의 주 구현 언어를 C++로 유지한다. PC Qt UI는 별도 프로젝트다. |
| 카메라·송출 | libcamera 기반 `libcamerasrc` → GStreamer → H.264 → MediaMTX | Pi의 카메라를 C++ 송출기 하나에서 열고 MediaMTX가 RTSP·WebRTC 시청자에게 전달한다. 현재 1280×720, 30fps다. |
| H.264 인코딩 | GStreamer `x264enc` | 현재 Pi의 `v4l2h264enc` 경로에서 프레임 처리 오류가 발생해 작동이 확인된 소프트웨어 인코딩을 사용한다. `ultrafast`, `zerolatency`, B 프레임 비활성화를 적용했다. 이전 시험에서 송출기 CPU 사용량은 약 115%였다. |
| 스트림 수명 | MediaMTX `runOnDemand` | 시청자가 접속할 때 카메라 송출기를 시작하고 시청자가 떠난 뒤 종료해 평상시 자원 사용을 줄인다. 첫 접속에는 카메라 시작 시간이 든다. |
| 서보 출력 | pigpio C API | GPIO18(PAN), GPIO19(TILT)에 서보 펄스폭을 지정하고 GPIO17 버튼 입력을 처리한다. 현재 각도 제한과 수동 제어는 [서보 코드](../pi/servo_test/src/main.cpp)에 있다. |
| 원격 서보 제어 | TCP 5000, 줄 단위 `PTZ:...`·`TRACK:ON/OFF` 명령 | PC Qt UI가 보내는 기존 명령 형식과 맞춘다. pigpio 사용은 Pi의 서보 서비스 한 곳에서 관리한다. |

현재 송출 코드는 [카메라 송출기](../pi/camera_stream/src/main.cpp), MediaMTX 설정은
[mediamtx.yml](../pi/camera_stream/mediamtx.yml)에 있다. 하드웨어 인코더 오류는
[트러블슈팅 기록](../troubleshotting.md)에 상세히 적혀 있다.

## 구현 중: 사람 객체 탐지와 자동 추적

**상태: C++ 구현, 모델 로딩, 실제 RTSP 송출과 Qt 메시지 경로를 확인했다.
사람을 따라 움직이는 서보 동작과 지연·탐지 품질은 추가 검증이 필요하다.**

목표 대상은 **사람 전체**다. 신경망 객체 탐지가 `person`의 위치 박스와 신뢰도를
산출하고, 대상 연결 로직이 여러 프레임에서 같은 사람을 선택한다. 그 결과의 중심과
화면 중심 사이 오차로 PAN/TILT 각도를 정한다. 별도의 추적기를 나중에 추가하더라도
신경망 탐지를 주기적으로 다시 수행해 대상을 확인한다.

### 영상 경로

카메라는 한 번만 열고 GStreamer의 `tee`와 분기별 `queue`로 압축 전 영상을
송출과 탐지로 나눈다. 탐지 경로는 640×360, 최대 10fps 입력으로 설정했다.
추론은 그보다 느릴 수 있으며 오래된 대기 프레임을 버린다. Pi가 자신의 RTSP 영상을
다시 수신·디코딩하면 불필요한 작업과 지연이 생긴다.

탐지기는 **현재 처리 중인 프레임 하나와 최신 대기 프레임 하나**만 보유한다. 새
프레임이 들어오면 오래된 대기 프레임을 교체한다. 30fps 입력에서 모델이 5fps밖에
처리하지 못할 때 모든 프레임을 보관하면 시간이 갈수록 오래된 사람 위치로 제어하기
때문이다. 추론 결과에는 촬영 시각을 붙여 너무 오래된 결과를 제어에서 제외한다.
송출 경로에는 독립된 큐를 사용해 탐지 처리 때문에 인코딩이 대기하지 않게 한다.
GStreamer의 [tee](https://gstreamer.freedesktop.org/documentation/coreelements/tee.html)와
[queue](https://gstreamer.freedesktop.org/documentation/coreelements/queue.html) 동작을
기준으로 설계한다.

### 탐지 모델과 실행 엔진

| 후보 | 선택 이유 | 결정에 필요한 검증 |
| --- | --- | --- |
| OpenCV 4.5.1 DNN + 사전 학습된 Caffe MobileNet-SSD 300×300 | **현재 기준 구현.** 설치된 OpenCV와 C++에서 시작하기 쉽다. 모델 로딩·추론은 통과했다. | 실제 사람 탐지 품질, 송출과 동시 실행 시 지연·CPU 경쟁 |
| TensorFlow Lite C++ + 양자화 SSD MobileNet | Raspberry Pi의 공식 객체 탐지 예제에도 사용된다. 모델 크기와 연산 비용을 낮출 가능성이 있다. | 이 Pi의 실행 엔진·연산 지원, 실제 추론 시간, 정확도, C++ 통합 비용 |

현재 OpenCV DNN을 사용한다. 송출 없는 시험에서 1/2/3스레드 추론 시간은 각각
약 412/229/192ms였다. 송출과 함께 실행한 짧은 시험에서는 2스레드가 약
284~319ms, 3스레드가 약 292~368ms였다. 3스레드는 모델 단독 시험에서만
빨랐기 때문에 실제 서비스는 **2스레드**로 유지한다. 이 값은 짧은 시험의 관측값이며
장시간 처리량과 탐지 정확도를 보장하지 않는다.
**최종 모델은 같은 장면에서 다른 후보도 측정한 뒤
재평가한다.** `person` 결과만 남기는 필터는 신경망 본체의 계산량을 크게 줄이지
못한다. 입력 영상을 더 작게 하면 작은 사람을 놓칠 수 있으므로 입력 크기도 탐지
품질과 함께 비교한다. 모델을 매번 새로 학습시키는 계획은 없다. 실제 장면에서
탐지 품질이 부족할 때 데이터 수집과 재학습 여부를 판단한다.

참고: [OpenCV 4.5.1 객체 탐지 예제](https://docs.opencv.org/4.5.1/js_object_detection_with_camera.html),
[Raspberry Pi 객체 탐지 예제](https://www.raspberrypi.com/documentation/computers/camera_software.html#object_detect_tf-stage).

### 서보 제어와 Qt 연결

자동 제어는 현재 화면의 오차에 따라 이동량을 정하고, 중앙 근처에는 허용 영역을
둔다. 한 번에 움직일 최대 각도와 속도를 제한하고, 오래된 목표 명령을 누적하지
않는다. 사람이 사라지면 이동을 멈춘다. 카메라가 움직이는 동안 사람 위치도 바뀌므로
서보에 명령한 각도를 실제 측정 각도로 간주하지 않는다. 수동 키·Qt 명령과 GPIO17
중앙 버튼은 자동 제어보다 우선하도록 설계한다.

Qt의 기존 `TRACK:ON/OFF` 요청을 서보 서비스의 추적 상태에 연결했다. Pi가 사람 탐지를
수행하므로 Qt 영상 수신 버퍼가 서보 제어 지연에 직접 들어가지 않는다. Qt에 사람
위치를 표시할 때 현재 Qt가 이해하는 8개 필드의 `DETECT` 메시지를 사용한다.
박스 크기나 촬영 시각을 Qt에 표시하려면 양쪽 메시지 형식을 함께 확장해야 한다.
현재 시청자 접속 시에만 카메라가 시작하므로, 첫 자동 추적 범위는 **Qt가 영상을 보고
있는 동안**으로 잡는다.

### 성능 최적화 우선순위

1. 현재 구성의 영상 지연, CPU·온도, 프레임 누락을 측정한다.
2. 하드웨어 H.264 인코딩 경로를 분리 검증한다. 이전 오류가 재현되면 현재 인코더를
   유지하며 30fps와 낮춘 프레임레이트의 품질·CPU·지연을 비교한다.
3. 최신 프레임만 처리하는 탐지 경로를 만들고 모델별 추론 시간과 사람 탐지 품질을
   **송출과 동시에** 측정한다. 추론 스레드 수를 늘리는 것도 전체 지연 기준으로
   평가한다.
4. 탐지 박스의 흔들림, 대상 소실, 서보 반응을 확인한 뒤 제어 간격과 허용 영역을
   조절한다. 별도 영상 추적기는 반복 탐지만으로 반응이 부족할 때 검토한다.
5. Qt의 실제 재생 방식에서 수신 버퍼와 RTSP TCP·UDP 또는 WebRTC의 영상 지연을
   비교한다. 수신 버퍼는 영상의 끊김과 지연을 함께 보고 결정한다.

## 2026-10-03: 서보 서비스 소스를 기능별로 분리

- 상태: 적용. C++17 함수 중심 구조를 유지한다.
- 목적: TCP 연결 관리, 명령 해석, GPIO 출력, 버튼, 터미널 입력을 각각 읽고
  수정할 수 있도록 구현 파일과 공개 선언을 나눈다.
- 선택 이유: `main.cpp`에서 시작·입력 대기·종료 순서를 한눈에 볼 수 있고,
  GPIO·각도 제한은 `config.h` 한 곳에서 확인할 수 있다. 공유 각도와 GPIO 쓰기는
  `servo/servo_control.cpp` 내부의 mutex로 보호하고 외부에는 함수로 접근하게 한다.
- 검증: CMake 빌드 완료. 가짜 GPIO를 사용하는 임시 시험으로 TCP 개행 처리,
  명령·각도 제한, 버튼 debounce, 키 입력, 종료 정리를 확인했다.
- 적용 범위: 실행 옵션, TCP 메시지 형식과 각도 제한을 유지하는 구조 정리다.
  추론 속도와 영상 지연의 개선 효과를 주장하는 변경은 아니다.
- 코드 안내: [서보 소스 구조](../pi/servo_test/README.md#소스-구조).

## 2026-10-06: 처리 구조의 근거를 남기는 계측 도구

- 상태: C++17 CSV 계측·자원 수집·소프트웨어 비교 시험 구현.
- 선택 이유: monotonic 시간과 PID/TID로 실행 주체를 구분하고, 부모 이벤트 ID로
  명령/버튼과 GPIO 호출을 연결한다. 별도 Linux 자원 수집기로 실행 로그의 책임과
  CPU/RSS 관측을 나눈다. 기본 운영에서는 환경변수 설정 없이 CSV를 쓰지 않는다.
- 비교: 실제 MobileNet-SSD와 x264를 합성 영상에서 실행해 탐지 OFF, 공유 경로
  동기 처리, 별도 탐지 스레드, FIFO/최신 정책, OpenCV 1/2/3스레드를 비교한다.
- 예비 결과: 최신 비동기는 인코딩 출력 약 30버퍼/s를 유지했고 동기는 약 11버퍼/s였다.
  FIFO는 모델 추론 시간이 짧아도 결과 나이가 길어졌다. 추론 속도만으로 제어 품질을
  평가하지 않는다. 2스레드 선택은 현재 예비 결과와 일치하지만 장시간 반복 확인이 필요하다.
- 한계: 합성 영상·1회 짧은 시험으로 실제 카메라/Qt/기계적 모터 지연을 확정하지 않는다.
  스레드 수 설정은 프로세스 전체 스레드 수가 아니며 수집 결과로 실제 수를 확인한다.
- 조건/결과: [성능 측정 안내](performance/README.md),
  [2026-10-06 예비 결과](performance/2026-10-06-results.md).

## 2026-10-07: ONVIF로 Pi의 RTSP URL 조회

- 상태: C++17 서비스 구현·설치·실행, Pi의 LAN 검색/조회 및 반환 URL 재생 정보 확인.
- 목적: PC Qt가 Pi를 검색하고 표준 Device/Media API로 RTSP 주소를 얻도록 한다.
  기존 ONVIF 규격을 사용하는 API 일부 구현이며 새 프로토콜을 설계하는 작업은 아니다.
- 구조: 별도 `pi/onvif_service` 프로세스가 UDP Probe/HTTP SOAP 요청에 응답한다.
  MediaMTX와 카메라 송출기는 기존 RTSP/on-demand 동작을 사용한다. URL 조회만으로
  카메라를 시작하지 않는다. PTZ/TRACK은 기존 TCP 5000 서비스를 사용한다.
- 선택 이유: 장치 검색·URL 조회는 짧은 요청으로 끝나므로 비블로킹 poll 이벤트 루프와
  연결별 수신/송신 버퍼를 사용한다. 인코딩·추론·GPIO를 이 프로세스에서 하지 않는다.
  별도 모델/추론 스레드나 요청별 스레드를 추가하지 않는다.
- XML: Pi에 설치된 Expat을 재사용해 namespace URI로 해석한다. 접두어 문자열에
  의존하는 파싱이나 단순 문자열 검색으로 SOAP 요청을 판별하지 않는다.
- 범위 선택: gSOAP로 전체 WSDL 코드를 생성하는 구성 대신 주소 조회에 필요한
  Device/Media API만 구현했다. 전체 장치 관리·인증·PTZ까지 확장할 때는 생성 코드와
  적합성 시험을 포함하는 구성을 다시 검토한다.
- 장치 식별: libuuid의 프로젝트별 namespace UUID로 machine-id를 변환해 안정적인

## 2026-10-07: ONVIF·영상 접속 계정 추가

- 상태: 사용자 지정 계정으로 ONVIF HTTP Digest와 MediaMTX 영상 인증 구현·적용.
- 선택 이유: Qt의 QAuthenticator와 연결할 수 있는 HTTP Digest를 사용한다. SHA-256과
  MD5를 제공하며 signed nonce(120초), 요청 카운터 재사용 방지, 병렬 도착 순서 허용
  창을 구현했다. UDP 장치 검색에는 계정 정보를 넣지 않는다.
- 저장: 실제 비밀번호는 저장소 밖 root/0600 파일에 둔다. systemd LoadCredential로
  ONVIF 서비스에 전달하며 MediaMTX의 실제 설정도 private 파일로 생성한다.
  비밀번호는 문서·소스·테스트 결과에 남기지 않는다.
- 영상: MediaMTX 내부 인증을 사용하고 외부 cam read 권한만 부여한다. Pi 내부
  loopback 송출·워치독·metrics는 예외로 유지한다. 재설치 시 계정 설정을 유지한다.
- 검증: CTest 3개 통과. HTTP Digest 누락/잘못된 계정/정상 계정, nonce 카운터 재사용,
  요청 URI 바인딩, 병렬 요청의 순서 변경을 검증했다. 실제 서비스에서도 ONVIF 조회와
  RTSP DESCRIBE의 정상/실패 접근을 확인했다.
- 범위: WS-Security UsernameToken, TLS, ONVIF 전체 적합성, 기존 TCP 5000 제어
  인증까지 구현한 것은 아니다. Digest 로그인과 영상 암호화는 구별한다.
- 근거: [HTTP Digest RFC 7616](https://www.rfc-editor.org/rfc/rfc7616),
  [MediaMTX 인증](https://mediamtx.org/docs/features/authentication),
  [Qt authenticationRequired](https://doc.qt.io/qt-6/qnetworkaccessmanager.html#authenticationRequired).

## 2026-10-07: 외부 PTZ 제어를 ONVIF로 전환

- 상태: 구현·테스트·서비스 적용 완료. PC Qt 변경은 별도 프로젝트에서 진행한다.
- 선택: GetServices/Media profile에 PTZ 서비스를 연결하고 표준 이동·정지·상태·설정
  조회를 제공한다. 인증은 기존 HTTP Digest를 재사용한다.
- GPIO 소유권: ONVIF는 좌표를 검증해 loopback RPC로 넘기고 서보 서비스만 GPIO를 쓴다.
  공통 제한값은 `common/control/ptz_limits.h`로 모아 변환/출력 범위가 달라지지 않게 한다.
- 동작: 서보의 단일 입력 루프에서 약 20ms마다 궤적 목표를 갱신한다. 별도 이동 스레드를
  추가하지 않는다. 버튼·수동·자동 제어는 같은 mutex와 취소 규칙을 사용한다.
- 연속 이동: 0.1~5초 Timeout을 두고 정지/만료/경계에서 목표 갱신을 중단한다.
  마지막 펄스는 유지한다. 위치·이동 상태는 명령/소프트웨어 기준이며 물리 피드백은 아니다.
- 이행: 외부 PTZ 문자열은 거부한다. Pi 로컬 키와 TRACK/탐지 알림 TCP는 유지한다.
- 확인: ONVIF CTest 4개, 순수 궤적 CTest 1개, 실제 제어 코드의 가짜 GPIO CTest 1개 통과.
  설치된 서비스에서 인증된 상태 조회·0변위/0속도/Stop 경로와 무인증 401을 확인했다.
- 남은 확인: 실제 PC Qt, 비영 이동의 실물 방향·속도, PAN 좌우 반전 보정, 타 클라이언트 호환성.
- 계약: [Qt PTZ 전환](onvif_ptz_qt_migration.md).
